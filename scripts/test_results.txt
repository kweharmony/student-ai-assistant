# Конспект лекции

## 🎯 Тема лекции
Проектирование логической и физической модели базы данных для системы учёта поставок автомобилей.

---

## 📌 Логическое проектирование БД

**Основные понятия:**
- **Объект** — сущность предметной области, которую можно "потрогать"
- **Связь** — отношение между объектами (1:1, 1:N, N:M)
- **Первичный ключ** — уникальный идентификатор записи
- **Внешний ключ** — ссылка на первичный ключ другой таблицы

**Ключевые тезисы:**
- Логическая модель отражает реальные объекты и связи между ними
- Связи программируются через внешние ключи
- Многие-ко-многим отношения требуют промежуточных таблиц
- Избыточные связи ухудшают производительность БД

**Пример:** Связь "поставщик-получатель" — один ко многим, так как один поставщик работает со многими получателями.

---

## 📌 Объекты предметной области

**Основные сущности:**
- **Поставщик** — организация, поставляющая автомобили
- **Получатель** — организация, принимающая автомобили  
- **Договор** — юридический документ между поставщиком и получателем
- **Акт** — документ передачи автомобилей по договору
- **Доверенность** — документ, уполномочивающий сотрудника
- **Сотрудник** — доверенное лицо, осуществляющее передачу
- **Автомобиль** — товар, передаваемый по акту

**Типы связей:**
- Поставщик → Договор: 1:N
- Получатель → Договор: 1:N  
- Договор → Акт: 1:N
- Доверенность → Акт: 1:N
- Акт → Автомобиль: 1:N

---

## 📌 Физическая модель данных

**Структура таблиц:**
- Каждая сущность становится отдельной таблицей
- Технические ключи (ID) для уникальной идентификации
- Альтернативные ключи для бизнес-идентификации
- Внешние ключи для реализации связей

**Пример таблиц:**
- `Suppliers` (ID, название, форма_собственности)
- `Clients` (ID, название, форма_собственности) 
- `Contracts` (ID, номер, дата, ID_поставщика, ID_клиента)
- `Acts` (ID, номер, дата, место, ID_договора, ID_доверенности)
- `Cars` (ID, ПТС, VIN, модель, ID_акта)

**Словари:**
- `Models` — модели автомобилей
- `Cities` — города поставки
- `Ownership_forms` — формы собственности

---

## 📌 Практическое применение

**Требования к проекту:**
- Минимум 30 таблиц
- Оригинальная предметная область
- Полноценная бизнес-логика
- Контрольные примеры данных

**Контрольный пример:**
- 2 получателя: ООО "Октябрь-Авто" и ООО "Сентябрь-Авто"
- По 1 договору с каждым
- 3 акта передачи
- 7 автомобилей разных моделей

**Пример запроса SQL:**
```sql
SELECT model 
FROM cars, acts, contracts, clients 
WHERE cars.id_act = acts.id 
  AND acts.id_contract = contracts.id 
  AND contracts.id_client = clients.id 
  AND clients.title = 'ООО Октябрь-Авто';
```

# 💡 Объяснение: "алгоритм построения логической схемы базы данных"

## 🎯 Суть одним предложении
*Это пошаговая инструкция, как превратить реальные бизнес-процессы в структуру таблиц базы данных, чтобы компьютер мог их обрабатывать.*

---

## 📖 Простое объяснение

Логическая схема базы данных — это "чертёж" того, как будут храниться данные. Представь, что ты проектируешь систему хранения документов для компании. Сначала ты анализируешь, какие сущности существуют (клиенты, договоры, поставщики), а потом определяешь, как они связаны между собой.

**Ключевые моменты:**
- Определяем сущности (объекты реального мира)
- Определяем связи между ними
- Выбираем тип связи (один-к-одному, один-ко-многим, многие-ко-многим)

---

## 🌟 Аналогия из жизни

**Представь, что построение логической схемы — это как организация библиотеки:**

Ты — библиотекарь, и тебе нужно организовать книги так, чтобы читатели могли быстро находить нужное. Сначала ты определяешь основные категории (художественная литература, научная, учебники) — это твои сущности. Потом определяешь связи: одна книга может быть только в одном разделе, но в одном разделе может быть много книг.

**Как они похожи:**
- 📚 Книги = записи в базе данных
- 📂 Разделы = таблицы
- 🔗 Система каталогов = связи между таблицами

**Важное отличие:**
В базе данных связи строго формализованы и подчиняются математическим правилам, а в библиотеке возможны исключения.

---

## 💻 Практический пример из лекции

**Задача:** Автопроизводитель (АвтоВАЗ) хочет отслеживать договоры с дилерами в разных городах.

**Решение:**
1. **Определяем сущности:** 
   - `Производитель` (АвтоВАЗ)
   - `Дилер` (Октябрь-Авто в Москве, СПб, Казани)
   - `Договор`

2. **Определяем связи:**
   - Один производитель → много дилеров (1:М)
   - Один дилер → много договоров (1:М)
   - Один договор → один производитель (1:1)

3. **Создаём структуру:**
```
Производитель (id, название)
Дилер (id, название, город, id_производителя)
Договор (id, дата_заключения, срок, id_дилера)
```

**Результат:** Теперь директор за обедом может за минуту узнать, сколько машин сбыл каждый дилер!

---

## 📊 Визуализация

```
Производитель (1) ←---→ (М) Дилер (1) ←---→ (М) Договор
     ↑                          ↑
     | 1:М                     | 1:М
     |                         |
(только один)           (много договоров
 производитель)          у каждого дилера)
```

**Объяснение схемы:**
- Стрелки показывают направление связи
- (1) — "один", (М) — "много"
- Каждый дилер привязан к одному производителю
- У каждого дилера может быть много договоров

---

## 🎓 Советы

**Как лучше усвоить:**
1. Рисуй схемы на бумаге для реальных ситуаций (магазин, университет, соцсеть)
2. Практикуйся определять тип связи в повседневной жизни (один студент — много оценок)

**Частые ошибки:**
- ⚠️ Путают "один-ко-многим" и "многие-ко-многим" — запомни: если у объекта А может быть много B, и у B может быть много A = многие-ко-многим
- ⚠️ Забывают, что связь "один-к-одному" используется редко — обычно когда нужно разделить чувствительные данные

# Вопросы для самопроверки по теме "Проектирование базы данных"

## 🎯 Базовый уровень (4 вопроса)

**1. Что такое логическая модель данных?**
*Краткий ответ:* Логическая модель данных - это схематическое представление структуры данных, которое показывает объекты (сущности), их атрибуты и связи между ними без привязки к конкретной СУБД.

**2. Перечислите основные типы связей между объектами в базе данных**
*Краткий ответ:* Один-к-одному (1:1), один-ко-многим (1:N), многие-ко-многим (M:N).

**3. Дайте определение понятию "первичный ключ"**
*Краткий ответ:* Первичный ключ - это уникальный идентификатор записи в таблице, который однозначно определяет каждую запись и не может содержать NULL-значений.

**4. Что такое внешний ключ и для чего он используется?**
*Краткий ответ:* Внешний ключ - это атрибут таблицы, который ссылается на первичный ключ другой таблицы, обеспечивая целостность связей между таблицами.

## 📊 Средний уровень (4 вопроса)

**5. Как спроектировать связь "многие-ко-многим" между двумя таблицами?**
*Краткий ответ:* Создается промежуточная таблица, содержащая первичные ключи обеих связанных таблиц. Например, для связи M:N между "Договоры" и "Автомобили" создается таблица "Акты передачи".

**6. Какие шаги нужно выполнить для создания физической модели данных?**
*Краткий ответ:* Определить таблицы и их атрибуты, задать типы данных, определить первичные и внешние ключи, установить ограничения целостности, нормализовать структуру.

*Краткий ответ:* Составной ключ состоит из нескольких атрибутов. Например, в таблице "Доверенности" ключ может состоять из "Номер доверенности" + "Дата выдачи". Используется, когда ни один атрибут не уникален сам по себе.

# Расширенный конспект лекции по проектированию базы данных

## Обзор темы
Лекция посвящена проектированию базы данных для системы учёта поставок автомобилей. Рассматривается процесс создания логической и физической модели данных на основе бизнес-процессов реальной компании. Студент научится преобразовывать бизнес-требования в структурированную базу данных.

---

## Термины и определения

### 🔹 Логическая модель данных

**Определение:**
Логическая модель данных — это абстрактное представление структуры данных, которое описывает сущности, их атрибуты и взаимосвязи без привязки к конкретной СУБД.

**Подробное объяснение:**
Логическая модель представляет собой концептуальное описание данных, которые необходимо хранить в системе. Она включает в себя:
- **Сущности** (объекты) — основные понятия предметной области (поставщик, получатель, договор и т.д.)
- **Атрибуты** — характеристики сущностей
- **Связи** — отношения между сущностями (один-к-одному, один-ко-многим, многие-ко-многим)

Логическая модель не зависит от технической реализации и служит мостом между бизнес-требованиями и физической реализацией. Она позволяет анализировать полноту охвата предметной области и выявлять потенциальные проблемы на ранних этапах проектирования.

**Практическое применение:**
- Проектирование информационных систем
- Анализ бизнес-процессов
- Документирование требований к данным
- Создание технического задания для разработчиков

**Связь с другими понятиями:**
Логическая модель является промежуточным звеном между концептуальной моделью (высокоуровневое описание) и физической моделью (реализация в конкретной СУБД).

**Примеры:**
- *Из лекции:* Модель поставок автомобилей с сущностями "Поставщик", "Получатель", "Договор", "Акт"
- *Дополнительно:* Модель интернет-магазина с сущностями "Покупатель", "Товар", "Заказ", "Оплата"

**Важно знать:**
Студенты часто путают логическую и физическую модели. Логическая модель описывает ЧТО хранить, физическая — КАК хранить.

---

### 🔹 Физическая модель данных

**Определение:**
Физическая модель данных — это реализация логической модели в конкретной системе управления базами данных (СУБД) с учётом технических ограничений и требований производительности.

**Подробное объяснение:**
Физическая модель включает:
- **Таблицы** с конкретными типами данных
- **Индексы** для ускорения поиска
- **Ограничения целостности** (первичные и внешние ключи)
- **Триггеры** и хранимые процедуры
- **Параметры хранения** (размеры табличных пространств, параметры файлов)

Модель оптимизируется под конкретную СУБД (MySQL, PostgreSQL, Oracle и др.) и учитывает такие факторы как объем данных, частота запросов, требования к производительности.

**Практическое применение:**
- Создание реальных баз данных
- Оптимизация производительности запросов
- Планирование масштабирования системы
- Миграция данных между разными СУБД

**Связь с другими понятиями:**
Физическая модель является реализацией логической модели и должна точно отражать все определённые в ней сущности и связи.

**Примеры:**
- *Из лекции:* Таблицы "suppliers", "clients", "contracts" с конкретными полями и типами данных
- *Дополнительно:* Таблицы "users", "products", "orders" в интернет-магазине с индексами на часто используемых полях

**Важно знать:**
При проектировании физической модели необходимо балансировать между нормализацией (устранение избыточности) и денормализацией (ускорение запросов).

---

### 🔹 Типы связей между сущностями

**Определение:**
Типы связей определяют, как сущности соотносятся друг с другом в реляционной модели данных.

**Подробное объяснение:**
Существует три основных типа связей:
1. **Один-к-одному (1:1)** — каждой записи в одной таблице соответствует не более одной записи в другой таблице
2. **Один-ко-многим (1:N)** — одной записи в таблице соответствует множество записей в связанной таблице
3. **Многие-ко-многим (M:N)** — множеству записей в одной таблице соответствует множество записей в другой таблице

Связи реализуются через механизм внешних ключей. Для связи многие-ко-многим создается промежуточная таблица, содержащая ключи обеих связанных таблиц.

**Практическое применение:**
- Проектирование структуры базы данных
- Обеспечение целостности данных
- Оптимизация запросов JOIN
- Проектирование интерфейсов приложений

**Связь с другими понятиями:**
Типы связей определяют структуру внешних ключей и влияют на производительность запросов.

**Примеры:**
- *Из лекции:* Связь "Поставщик-Договор" — один-ко-многим (один поставщик заключает много договоров)
- *Дополнительно:* Связь "Студент-Курс" — многие-ко-многим (много студентов посещают много курсов)

**Важно знать:**
Неправильное определение типа связи может привести к избыточности данных или невозможности корректно отразить бизнес-логику.

---

### 🔹 Первичный ключ (Primary Key)

**Определение:**
Первичный ключ — это поле или набор полей таблицы, которые однозначно идентифицируют каждую запись в таблице.

**Подробное объяснение:**
Первичный ключ обладает следующими свойствами:
- **Уникальность** — каждая запись имеет уникальное значение ключа
- **Непустота** — значение ключа не может быть NULL
- **Неизменяемость** — значение ключа не должно изменяться в течение жизни записи

Первичные ключи бывают:
- **Естественные** — основаны на реальных данных (номер паспорта, ИНН)
- **Суррогатные** — искусственно созданные идентификаторы (автоинкрементные числа, GUID)

**Практическое применение:**
- Обеспечение уникальности записей
- Создание связей между таблицами
- Ускорение поиска записей
- Поддержание целостности данных

**Связь с другими понятиями:**
Первичный ключ используется для создания связей через внешние ключи в связанных таблицах.

**Примеры:**
- *Из лекции:* ID поставщика, ID договора, ID автомобиля
- *Дополнительно:* Номер заказа, ID пользователя, артикул товара

**Важно знать:**
Выбор между естественным и суррогатным ключом зависит от конкретной ситуации. Суррогатные ключи более стабильны, но естественные могут быть более понятны пользователям.

---

### 🔹 Внешний ключ (Foreign Key)

**Определение:**
Внешний ключ — это поле в таблице, которое ссылается на первичный ключ другой таблицы, устанавливая связь между записями.

**Подробное объяснение:**
Внешний ключ обеспечивает референциальную целостность данных. Он гарантирует, что:
- Значение внешнего ключа должно существовать в связанной таблице
- При удалении записи в главной таблице можно настроить каскадные операции

Ограничения внешнего ключа:
- **RESTRICT** — запрещает удаление, если есть ссылающиеся записи
- **CASCADE** — удаляет/обновляет связанные записи
- **SET NULL** — устанавливает NULL в связанных записях

**Практическое применение:**
- Поддержание целостности данных
- Создание связей между таблицами
- Автоматическое обновление связанных данных
- Предотвращение "осиротевших" записей

**Связь с другими понятиями:**
Внешний ключ всегда ссылается на первичный ключ другой таблицы и реализует связи между сущностями.

**Примеры:**
- *Из лекции:* В таблице "contracts" поле "supplier_id" ссылается на "suppliers.id"
- *Дополнительно:* В таблице "orders" поле "customer_id" ссылается на "customers.id"

**Важно знать:**
Неправильная настройка каскадных операций может привести к непреднамеренному удалению большого количества данных.

---

### 🔹 Нормализация базы данных

**Определение:**
Нормализация — это процесс организации данных в базе данных для уменьшения избыточности и улучшения целостности данных.

**Подробное объяснение:**
Нормализация выполняется через серию нормальных форм:
1. **Первая нормальная форма (1NF)** — устранение повторяющихся групп, атомарность данных
2. **Вторая нормальная форма (2NF)** — устранение частичных зависимостей
3. **Третья нормальная форма (3NF)** — устранение транзитивных зависимостей
4. **Нормальная форма Бойса-Кодда (BCNF)** — усиленная третья нормальная форма

Каждая нормальная форма решает определенные проблемы проектирования и приближает структуру базы данных к идеальной.

**Практическое применение:**
- Устранение аномалий вставки, обновления и удаления
- Снижение избыточности данных
- Упрощение поддержки базы данных
- Улучшение целостности данных

**Связь с другими понятиями:**
Нормализация влияет на структуру таблиц, типы связей и производительность запросов.

**Примеры:**
- *Из лекции:* Разделение данных о поставщике и получателе в разные таблицы вместо хранения в одной
- *Дополнительно:* Выделение таблицы "адреса" вместо хранения адресов в таблице "клиенты"

**Важно знать:**
Чрезмерная нормализация может ухудшить производительность. Иногда целесообразна денормализация для часто выполняемых запросов.

## Алгоритмы и методы

### 🔸 Алгоритм проектирования базы данных

**Назначение:**
Для систематического создания оптимальной структуры базы данных, соответствующей бизнес-требованиям.

**Пошаговая инструкция:**

1. **Анализ предметной области**
   - Что делать: Изучить бизнес-процессы, выявить основные сущности и их атрибуты
   - Зачем: Понимание того, какие данные нужно хранить и как они связаны
   - Пример: В системе поставок автомобилей выявить сущности "Поставщик", "Получатель", "Договор", "Автомобиль"

2. **Создание логической модели**
   - Что делать: Определить сущности, их атрибуты и типы связей между ними
   - Зачем: Создать абстрактное представление структуры данных
   - Пример: Нарисовать диаграмму сущность-связь с указанием типов связей

3. **Нормализация**
   - Что делать: Привести модель к требуемой нормальной форме
   - Зачем: Устранить избыточность и аномалии данных
   - Пример: Проверить, что все атрибуты зависят только от первичного ключа

4. **Создание физической модели**
   - Что делать: Преобразовать логическую модель в конкретные таблицы с типами данных
   - Зачем: Реализация модели в выбранной СУБД
   - Пример: Создать SQL-скрипты для создания таблиц с указанием типов полей

5. **Реализация в СУБД**
   - Что делать: Выполнить SQL-скрипты создания базы данных
   - Зачем: Создать работающую базу данных
   - Пример: CREATE TABLE suppliers (id INT PRIMARY KEY, name VARCHAR(100))

**Результат:**
Готовая к использованию база данных, соответствующая бизнес-требованиям.

**Практический пример:**
Проектирование базы данных для системы учёта поставок автомобилей с таблицами: suppliers, clients, contracts, acts, cars.

**Советы:**
- Начинайте с простой модели и постепенно усложняйте
- Тестируйте модель на реальных данных
- Учитывайте будущие требования к масштабированию
- Документируйте все принятые решения

---

### 🔸 Алгоритм определения типа связи

**Назначение:**
Для корректного определения типа связи между сущностями в логической модели.

**Пошаговая инструкция:**

1. **Анализ бизнес-правил**
   - Что делать: Изучить, как сущности взаимодействуют в реальном мире
   - Зачем: Понимание кардинальности связей
   - Пример: Один поставщик может заключать много договоров → связь 1:N

2. **Формулировка вопроса**
   - Что делать: Сформулировать вопрос о количестве связанных записей
   - Зачем: Четкое определение типа связи
   - Пример: "Сколько договоров может быть у одного поставщика?" и "Сколько поставщиков у одного договора?"

3. **Определение типа связи**
   - Что делать: На основе ответов определить тип связи (1:1, 1:N, M:N)
   - Зачем: Корректное проектирование структуры базы
   - Пример: Если ответы "много" и "один" → связь 1:N

4. **Проверка на избыточность**
   - Что делать: Убедиться, что связь не является избыточной
   - Зачем: Избежание ненужной сложности
   - Пример: Связь "Договор-Автомобиль" может быть избыточной, если есть связь через "Акт"

**Результат:**
Корректно определенный тип связи между сущностями.

**Практический пример:**
Определение связи между "Сотрудник" и "Доверенность" как 1:N (один сотрудник может иметь много доверенностей).

**Советы:**
- Всегда рассматривайте связь в обе стороны
- Учитывайте временные аспекты (связи могут меняться со временем)
- Тестируйте на граничных случаях
- Консультируйтесь с экспертами предметной области

## 🧮 Формулы и расчёты

### Формула определения количества таблиц

**Формула:** `T = E + L`

**Обозначения:**
- T = общее количество таблиц
- E = количество сущностей (entities)
- L = количество связей многие-ко-многим, требующих промежуточных таблиц

**Когда применять:**
При оценке сложности проекта базы данных и планировании ресурсов.

**Пример расчёта:**
Если в модели 6 сущностей и 2 связи многие-ко-многим:
T = 6 + 2 = 8 таблиц
