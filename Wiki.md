## 📌 **1. Проблема: Полная неопределённость в начале — «С чего начать?»**

`#организация`

**Контекст**:  
В первые дни после утверждения темы команда испытывала ощущение «информационного паралича». Была идея, но не было чёткого понимания, какие шаги делать первыми. Мы обсуждали дизайн, ИИ, тайм-менеджмент одновременно — и ни к чему не приходили. Проект стоял на месте.

**Последствия**:  
— Потеря 3–4 дней без прогресса.  
— Раздражение и снижение мотивации.  
— Ощущение, что «всё слишком сложно».

**Решение**:  
Провели дискуссию (3 часа), где:

- Чётко определили **MVP** (минимально жизнеспособный продукт):  
  _«Пользователь загружает аудио → получает обработанный конспект»_.
- Разбили работу на **роли** и **этапы**.
- Создали **дорожную карту на 10 недель** с еженедельными целями.

**Итог**:  
Появился **план действий**. Даже простой список «сначала регистрация, потом загрузка файла» дал ощущение контроля.  
✅ **Урок**: _Без плана — только хаос. Даже грубый план лучше, чем его отсутствие._

## 📌 **2. Проблема: Разрозненное хранение информации — «Где это обсуждалось?»**

`#организация`

**Контекст**:  
Идеи, требования, решения обсуждались в Telegram, на встречах, в личных заметках. Через неделю никто не мог вспомнить:  
— Где мы решили хранить файлы?  
— Какой цвет выбрать для интерфейса?  
— Кто отвечает за Whisper?

**Последствия**:  
— Повторные обсуждения одних и тех же вопросов.  
— Потеря важных решений.  
— Сложность вовлечения нового участника.

**Решение**:  
Ввели **единое пространство знаний**:

- **Obsidian** — для написания идей, промптов, архитектурных решений, ведения этого журнала.  
  → Преимущество: связи между заметками, удобное локальное хранение + синхронизация через облако.
- **Yandex Disk** — синхронизация для общих документов: ТЗ, презентации, скриншоты, аудиозаписи для тестов.  
  → Все файлы в папке `/Проектный практикум 2 курс`.

**Итог**:  
Теперь любой вопрос начинается с: «Посмотри в Вики».  
✅ **Урок**: _Если знание не задокументировано — его нет._

## 📌 **3. Проблема: Блокировка на этапе дизайна — «Как должен выглядеть сайт?»**

`#дизайн`

**Контекст**:  
Команда долго спорила о внешнем виде:  
— Современный или минималистичный?  
— Тёмная или светлая тема?  
— Кнопки с тенями или плоские?

Мы тратили время на Figma-макеты, хотя функционал ещё не работал.

**Последствия**:  
— Отвлечение от главного — логики и ИИ.  
— Ощущение, что «пока дизайн не готов — ничего не начнёшь».

**Решение**:  
Приняли **дизайнерское решение раз и навсегда**:

- **Цветовая палитра**: тёмно-синий (#0a0e1f) + белый (#e9effa) + акцент — светло-голубой (#99b5ea).  
  → Вдохновлено интерфейсами сайтов с похожим функционалом — лаконично, спокойно, фокус на контенте.
- **Принцип**: «Сначала работает — потом красиво».  
  → Верстка на чистом HTML + CSS, в будущем перенос на React + Tailwind CSS.

**Итог**:  
Дизайн перестал быть препятствием. Интерфейс получился **единым и профессиональным**, без лишних споров.  
✅ **Урок**: _Ограничь выбор — и получишь свободу действий._

## 📌 4. Проблема: Отсутствие чёткого разделения задач между участниками\*\*

`#организация`

**Контекст**:  
В начале все «немного делали всё»: фронт, бэк, ИИ. В итоге:

- Никто не чувствовал ответственности за конкретный блок.
- Возникали конфликты: «Я думал, ты делаешь аутентификацию!»

**Решение**:  
Формализовали роли и зоны ответственности:

| Участник              | Зона ответственности                             |
| --------------------- | ------------------------------------------------ |
| **Фронтенд + бэкенд** | Аутентификация, API, хранение файлов, UI         |
| **ML-спец по звуку**  | Whisper: транскрибация, предобработка аудио      |
| **ML-спец по тексту** | LLM-обработка, промпты, тайм-менеджмент (логика) |

- Ввели правило: **каждая задача в трекере имеет одного ответственного**.

**Итог**:  
Прогресс стал измеримым. Каждый знает, за что отвечает.  
✅ **Урок**: _Чёткие границы — основа командной работы._

## 📌 **6. Проблема: Параллельный запуск Whisper приводит к перегрузке сервера**

`#ml`

**Контекст**:  
При локальном запуске Whisper на сервере с 8 ГБ RAM (например, Aeza.net Shared) выяснилось:

- Каждая транскрибация потребляет 3–4 ГБ оперативной памяти,
- Два и более одновременных запроса вызывают замедление в 2–3 раза или полный крах сервиса,
- Для 1000 пользователей это неприемлемо, даже при использовании очередей.

**Решение**:  
Отказались от локального Whisper в пользу **внешнего API для транскрибации**:

- Выбрали провайдера с поддержкой русского языка и разумной стоимостью (например, Deepgram, AssemblyAI или другой),
- Аудиофайл загружается с фронтенда → передаётся напрямую во внешний API → результат возвращается в наш бэкенд,
- Наш сервер **не тратит CPU/RAM** на обработку — только передаёт данные.

**Итог**:  
Сервер остаётся **лёгким и стабильным**, обработка масштабируется автоматически, а стоимость предсказуема (~$0.01 за 10-минутную лекцию).  
✅ **Урок**: _Иногда проще доверить сложную задачу специализированному сервису, чем пытаться решить её локально._
