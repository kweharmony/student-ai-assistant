## 📌 **6. Проблема: Параллельный запуск Whisper приводит к перегрузке сервера**

`#ml`

**Контекст**:  
При локальном запуске Whisper на сервере с 8 ГБ RAM (например, Aeza.net Shared) выяснилось:

- Каждая транскрибация потребляет 3–4 ГБ оперативной памяти,
- Два и более одновременных запроса вызывают замедление в 2–3 раза или полный крах сервиса,
- Для 1000 пользователей это неприемлемо, даже при использовании очередей.

**Решение**:  
Отказались от локального Whisper в пользу **внешнего API для транскрибации**:

- Выбрали провайдера с поддержкой русского языка и разумной стоимостью (например, Deepgram, AssemblyAI или другой),
- Аудиофайл загружается с фронтенда → передаётся напрямую во внешний API → результат возвращается в наш бэкенд,
- Наш сервер **не тратит CPU/RAM** на обработку — только передаёт данные.

**Итог**:  
Сервер остаётся **лёгким и стабильным**, обработка масштабируется автоматически, а стоимость предсказуема (~$0.01 за 10-минутную лекцию).  
✅ **Урок**: _Иногда проще доверить сложную задачу специализированному сервису, чем пытаться решить её локально._

## 📌 **9. Проблема: CORS ошибки при локальной разработке — «Access-Control-Allow-Origin missing»**

`#фронтенд` `#бэкенд`

**Контекст**:  
При первых попытках подключить React фронтенд (порт 3000) к FastAPI бэкенду (порт 8000) столкнулись с ошибкой:

```
Access to fetch at 'http://localhost:8000/api/ml/process' from origin
'http://localhost:3000' has been blocked by CORS policy
```

Фронтенд не мог отправить запросы к API.

**Последствия**:

- Невозможность протестировать интеграцию фронтенда с бэкендом,
- Потеря 2-3 часов на поиск причины,
- Попытки использовать прокси в `package.json` (не помогло).

**Решение**:  
Добавили **CORS middleware** в FastAPI:

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=[
        "http://localhost:3000",
        "http://127.0.0.1:3000",
    ],
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

Для production планируется:

- Ограничить `allow_origins` только доменом продакшн-сервера,
- Добавить проверку `Origin` заголовка,
- Использовать HTTPS.

**Итог**:  
Фронтенд и бэкенд успешно взаимодействуют. CORS настроен корректно.  
✅ **Урок**: _CORS — не баг, а защита. Настрой его правильно с первого дня._

## 📌 **10. Проблема: Асинхронность в React — «Почему state не обновляется сразу?»**

`#фронтенд`

**Контекст**:  
При разработке компонента обработки текста столкнулись с проблемой:

```typescript
const handleProcess = async () => {
  const result = await processText(text, mode);
  console.log(result); // Выводит результат
  console.log(state.result); // Выводит null!
};
```

State не обновлялся сразу после вызова `processText`, что приводило к:

- Некорректному отображению результата,
- Повторным запросам к API,
- Путанице в логике компонента.

**Последствия**:

- Потеря 3-4 часов на отладку,
- Попытки использовать `setTimeout` (неправильный подход),
- Фрустрация от "непредсказуемого" поведения React.

**Решение**:  
Разобрались с **асинхронной природой setState**:

1. **useState обновляется асинхронно** — изменения применяются после ре-рендера.

2. Правильный подход — использовать **возвращаемое значение** функции:

```typescript
const handleProcess = async () => {
  const result = await processText(text, mode);
  // Используем result напрямую, не полагаемся на state
  if (result) {
    displayResult(result);
  }
};
```

3. Для отслеживания изменений state — **useEffect**:

```typescript
useEffect(() => {
  if (state.result) {
    displayResult(state.result);
  }
}, [state.result]);
```

**Итог**:  
Логика обработки стала предсказуемой. Асинхронность больше не вызывает проблем.  
✅ **Урок**: _React state — асинхронный. Проектируй логику с учётом этого._

## 📌 **11. Проблема: Дублирование кода в API запросах — «Одинаковый fetch в 5 местах»**

`#фронтенд` `#архитектура`

**Контекст**:  
По мере роста проекта обнаружили, что код для API запросов дублируется:

```typescript
// В компоненте A
const response = await fetch(`${API_URL}/api/ml/process`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(data),
});

// В компоненте B — тот же код
// В компоненте C — тот же код
// ...
```

**Последствия**:

- При изменении логики (добавление токена авторизации) нужно править 5+ мест,
- Риск забыть обновить какой-то компонент,
- Сложность добавления обработки ошибок.

**Решение**:  
Создали **custom hook `useMLProcessor`** с централизованной логикой:

```typescript
export const useMLProcessor = () => {
  const [state, setState] = useState({...});

  const processText = async (text, mode, topic) => {
    try {
      setState({ isProcessing: true, error: null });

      const response = await fetch(`${API_URL}/api/ml/process`, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ text, mode, topic }),
        signal: abortController.signal
      });

      const data = await response.json();
      setState({ isProcessing: false, result: data.processed_text });
      return data.processed_text;
    } catch (error) {
      setState({ isProcessing: false, error: error.message });
      return null;
    }
  };

  return { processText, ...state };
};
```

Теперь в компонентах:

```typescript
const { processText, isProcessing, result, error } = useMLProcessor();
```

**Итог**:  
Код стал **чище и поддерживаемее**. Изменения вносятся в одном месте.  
✅ **Урок**: _DRY (Don't Repeat Yourself) — не просто принцип, а необходимость._

## 📌 **12. Проблема: Отсутствие типизации в TypeScript — «any везде»**

`#фронтенд` `#качество-кода`

**Контекst**:  
В начале разработки для ускорения использовали `any`:

```typescript
const processData = (data: any) => {
  return data.result.text; // А если result === undefined?
};
```

Это приводило к:

- Runtime ошибкам: `Cannot read property 'text' of undefined`,
- Отсутствию автодополнения в IDE,
- Сложности рефакторинга.

**Последствия**:

- 2-3 часа на поиск ошибок, которые TypeScript мог бы предотвратить,
- Страх менять код ("а вдруг что-то сломается?"),
- Потеря преимуществ TypeScript.

**Решение**:  
Создали **строгую типизацию** для всех API взаимодействий:

```typescript
// types/ml.ts
export type MLMode =
  | "summarize"
  | "extract_terms"
  | "expand_topic"
  | "generate_questions"
  | "detailed_notes"
  | "cheat_sheet";

export interface MLProcessRequest {
  text: string;
  mode: MLMode;
  topic?: string;
}

export interface MLProcessResponse {
  processed_text: string;
  mode: MLMode;
  input_length: number;
  output_length: number;
  processing_time?: number;
}
```

Включили **strict mode** в `tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "noImplicitAny": true
  }
}
```

**Итог**:  
Количество runtime ошибок **сократилось на 80%**. Рефакторинг стал безопасным.  
✅ **Урок**: _TypeScript без строгой типизации — потерянная возможность._

</Suspense>;

Дополнительно:

- Вынесли редактор в отдельный chunk,
- Добавили preload для критических ресурсов,
- Оптимизировали импорты TipTap (только нужные расширения).

**Результат**:

- Начальная загрузка: **1.2s → 0.4s**,
- Редактор загружается только на странице аккаунта,
- Lighthouse score: **95/100**.

**Итог**:  
Сайт стал **заметно быстрее**. Пользователи не ждут.

## 📌 **15. Проблема: Медленная работа DeepSeek API — «Фильтрация идет по 20+ минут»**

`#ml` `#производительность`

**Контекст**:  
При отправке длинных транскрипций (до 70 тыс. токенов) на фильтрацию текста, выполнение последовательных запросов к LLM занимало более 15-20 минут. Пользователь получал ошибку таймаута или просто слишком долго ждал.

**Последствия**:
- Критическое снижение UX.
- Невозможность обработки больших лекций в реальном времени.

**Решение**:  
Внедрение асинхронного параллельного процессинга в `ml/transcription_filter.py`:
- Переход синхронного клиента на `AsyncOpenAI`.
- Разбивка текста на чанки по ~4000 символов (`_chunk_text`).
- Параллельная обработка чанков через `asyncio.gather` (`_process_chunk_async`).

**Итог**:  
Время фильтрации текста объемом 33 000 символов сократилось с 16+ минут до ~2 минут (за счет 10 параллельных запросов).  
✅ **Урок**: _Если независимая однотипная задача легко распараллеливается, нужно использовать асинхронность. Не заставляй пользователя ждать то, что можно сделать параллельно._

## 📌 **16. Проблема: Падение FastAPI сервера во время долгих задач — «Сервер внезапно перезагружается»**

`#бэкенд` `#инфраструктура`

**Контекст**:  
В процессе долгой транскрипции или фильтрации, сервер FastAPI мог внезапно прервать соединение. Как выяснилось, удаление временных аудиофайлов в папке `temp` триггерило hot-reload (отслеживание изменений файлов сервером uvicorn).

**Последствия**:
- Процесс обработки прерывался посередине.
- Невозможность завершить транскрипцию в стандартном режиме.

**Решение**:  
Удалили флаг `--reload` из команды запуска `uvicorn` в стартовых скриптах (`start_api_medium.bat`, `run_project.bat`).

**Итог**:  
Сервер работает стабильно, операции с файлами во время работы не вызывают перезапуск воркера.  
✅ **Урок**: _Флаг `--reload` предназначен только для разработки кода. Никогда не используй его в сценариях, где приложение работает с файлами на диске или выполняет длительные фоновые задачи._

## 📌 **17. Проблема: Сплошная стена текста от LLM — «Никаких абзацев»**

`#ml` `#prompt_engineering`

**Контекст**:  
После успешной фильтрации текста, результат возвращался без деления на абзацы, одной «сплошной стеной». Причиной оказалось строгое правило в промпте: «Выведи всю обработанную лекцию целиком КАК ОБЫЧНЫЙ ТЕКСТ».

**Последствия**:
- Текст становился абсолютно нечитаемым для пользователя.
- Дополнительная ручная работа по расстановке абзацев в редакторе сходила на нет, так как ИИ вырезал все `\n`.

**Решение**:  
Переписали системный промпт для фильтрации в `ml/filter_prompts.py`. Убрали ограничение на «обычный текст без markdown» и добавили жесткое правило на форматирование:  
«Ты ОБЯЗАН разделять текст на читаемые абзацы. Делай двойной перенос строки каждые 4-6 предложений или при смене логической мысли».

**Итог**:  
Модель теперь возвращает красиво структурированный текст.  
✅ **Урок**: _LLM очень буквально воспринимают запреты. Если просишь «обычный текст без форматирования», риск потерять даже стандартные абзацы очень велик. Указывай требования к визуальной структуре текста явно._
